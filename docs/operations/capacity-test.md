# آزمون ظرفیت رسانه — TASK-067

## وضعیت اجرا

**نتیجهٔ این محیط: اجرا نشد؛ بنابراین ظرفیت واقعی/حداکثر قابل پشتیبانی اعلام نمی‌شود.** در محیط توسعهٔ Windows این نوبت Docker، آدرس LiveKit عملیاتی، اعتبارنامهٔ جلسه و میزبان Linux در اختیار نیست. آزمون خودکار نرم‌افزار به‌جای اتصال رسانهٔ واقعی یا ارقام ساختگی استفاده نشده است. Issue #79 باید تا اجرای ماتریس واقعی زیر باز بماند.

این سند روش اجرای قابل‌تکرار، جمع‌آوری منابع و فرم ثبت نتایج را آماده می‌کند. منابع باید روی همان میزبان‌های API، PostgreSQL، LiveKit و coturn ثبت شوند؛ یک ماشین کلاینت/تولید بار جداگانه باشد تا CPU کلاینت با مصرف سرویس اشتباه نشود.

## پیش‌شرط و ایمنی

1. محیط آزمایشی جدا از production با TLS، imageهای LiveKit/coturn دقیق و ثبت‌شده، و شبکه/فایروال مطابق `deploy/media/README.md` آماده کنید.
2. از tenant، حساب‌ها و جلسه‌های آزمایشی استفاده کنید؛ دادهٔ واقعی سازمانی وارد نکنید. توکن LiveKit کوتاه‌عمر و محدود به اتاق باشد؛ API/metrics/TURN secret در ticket، log یا خروجی نمونه‌بردار ثبت نشود.
3. نسخهٔ API/Web، PostgreSQL، LiveKit، coturn، مرورگر/OS کلاینت‌ها، مشخصات VM، تعداد replica، region، RTT و پهنای باند را قبل از آزمون ثبت کنید.
4. بارگذاری را مرحله‌ای انجام دهید: ۲، ۱۰ و ۲۵ شرکت‌کننده در **هر اتاق**. پس از ۵ دقیقه warm-up، هر پله را حداقل ۱۵ دقیقه نگه دارید و هر پله را سه بار اجرا کنید. بین پله‌ها سرویس‌ها را به حالت پایه برگردانید و نتیجه را تأیید کنید.
5. در سناریوی پایه همه با audio/video منتشر کنند و همهٔ trackهای موردنیاز سناریوی محصول را دریافت کنند؛ سپس سناریوی audio-only را جداگانه بسنجید. ثبت کنید آیا share screen فعال بوده است. تعداد publisher و subscriber را جداگانه بنویسید؛ «تعداد participant» به‌تنهایی بار شبکه را تعیین نمی‌کند.
6. دو دستگاه واقعی ابتدا با `docs/operations/media-acceptance.md` اتصال و صدا/تصویر را تأیید کنند. اگر این smoke test شکست خورد، آزمون ظرفیت شروع نشود.

## اجرا و اندازه‌گیری

1. اتاق آنلاین آزمایشی را با API ایجاد کنید و برای هر شرکت‌کننده از مسیر مجاز `POST /api/v1/meetings/{id}/room/join` توکن جدا بگیرید. کلید مدیریتی LiveKit را به generator ندهید.
2. شرکت‌کنندگان را از چند کلاینت مستقل و شبکهٔ رسانهٔ واقعی وصل کنید. برای هر مرحله زمان شروع/پایان، تعداد تلاش/اتصال موفق، زمان اتصال، قطع/اتصال مجدد، packet loss و کیفیت مشاهده‌شده را ثبت کنید. بارساز نباید همهٔ WebRTC را از یک مرورگر/ماشین سنگین تولید کند.
3. روی میزبان Linux از مدت آزمون snapshot بگیرید:

   ```bash
   chmod +x deploy/media/scripts/sample-capacity.sh
   deploy/media/scripts/sample-capacity.sh /var/tmp/ksc-capacity-run-2.log 1200 5
   ```

   آرگومان‌ها به‌ترتیب مسیر خروجی، مدت به ثانیه و فاصلهٔ نمونه‌برداری‌اند. اسکریپت `uptime`، حافظه و دیسک میزبان، بایت شبکهٔ interfaceها و CPU/RAM/Network/Block IO/PID کانتینرها را با خروجی کم‌مجوز جمع می‌کند. برای اجزای خارج Docker و metrics برنامه، Prometheus را هم‌زمان scrape کنید؛ متریک API را با token محافظت‌شده بگیرید و مقدار token را در shell history نگذارید.
4. p50/p95/p99 زمان اتصال/درخواست، نرخ موفقیت، خطا و reconnect را از timestampهای generator محاسبه کنید. CPU/RSS/network هر جزء، میزان رشد حافظه، ترافیک و packet loss را در طول پله‌ها مقایسه کنید. زمان/نسخه/تنظیمات هر سه تکرار یکسان باشد.
5. حد توقف از پیش تعیین کنید (مثلاً افزایش خطا/قطع، مصرف پایدار بالای ۸۰٪ CPU، کمبود حافظه یا loss قابل مشاهده). اگر حد توقف رد شد، بار را زیاد نکنید؛ خروجی و محدودیت را ثبت کنید. این اعداد حد حفاظتی آزمون‌اند، نه SLO مصوب.

## تفسیر و محدودیت

- یک نتیجه فقط برای همان نسخه، توپولوژی، کدک، کیفیت تصویر، نسبت publisher/subscriber و شرایط شبکه معتبر است؛ آن را به «حداکثر کاربران سیستم» تعمیم ندهید.
- رسانهٔ WebRTC و signaling بارهای متفاوت دارند. CPU، NIC و relay usage در LiveKit/coturn را جداگانه بررسی کنید؛ TURN relay الزاماً مسیر همهٔ کاربران نیست.
- ظرفیت نهایی، اندازهٔ VM و SLO تا ثبت نتایج تکرارشده و تأیید هدف latency/availability توسط مالک محصول **تعیین نشده** است. برای production همچنان تصمیم No-Go در [گزارش PoC](poc-report.md) برقرار است.
